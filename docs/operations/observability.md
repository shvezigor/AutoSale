# Спостережуваність AutoSale

## Питання чергового інженера

1. На якому кроці зупинилося конкретне замовлення від Meta webhook до Google Sheets?
2. Яка частка normalization та Sheets export завершується помилкою?
3. Чи росте черга незавершених експортів?
4. Чи зросла тривалість HTTP-запитів або зовнішніх операцій?

## Кореляція та логи

API приймає безпечний `x-request-id` або генерує UUID і повертає його у відповіді. Для фонового Instagram-процесу `correlationId` дорівнює ID збереженої webhook-події. Цей самий ID відновлюється через trigger message під час експорту замовлення в Google Sheets.

Логи записуються як один JSON-об’єкт на рядок. Поля з назвами `token`, `secret`, `password`, `authorization`, `cookie`, `phone`, `email`, `address`, `payload` і `body` автоматично замінюються на `[REDACTED]`. Не додавайте до логів повні DTO або request body.

## Метрики

- API у внутрішній Docker-мережі: `GET http://api:3001/metrics`
- Worker у внутрішній Docker-мережі: `GET http://worker:3002/metrics`
- Web server records `web_upstream_slow` when an internal API call takes at least 1 second and `web_upstream_failed` for API 5xx or network failure. These JSON log events contain only a bounded route group (`orders`, `auth`, etc., otherwise `other`), status class, elapsed milliseconds and a generated request ID. The same ID is forwarded as `x-request-id` to the API and appears in its existing request-completion log. Never log the full URL, query string, cookies, response body or exception message. These events measure the **web → API hop**, not the full browser navigation, Next rendering or Cloudflare tunnel; compare them with API histograms before attributing a slow page to the database.
- Caddy writes scoped access timing for exact `/dashboard` and `/orders` paths to `/data/workspace-navigation-timing.log` inside the proxy container. The JSON entries contain only a fixed `route` label (`dashboard` or `orders`), response status, duration in milliseconds, response size and Caddy's non-request log metadata. The request object, response headers and even Caddy's currently empty `user_id` field are removed before encoding; all other paths are skipped. The file rolls at 10 MiB, keeps at most three rotated files and expires rotated files after seven days. Read it locally with `docker exec autosale-proxy-1 tail -n 50 /data/workspace-navigation-timing.log`; do not copy raw logs into tickets. This measures time at Caddy through the upstream response, **not** Cloudflare, browser rendering or the complete click-to-visible transition. Run `infra/scripts/verify-caddy-route-timing.ps1` before changing the Caddy logging contract; its isolated-container probe checks route scope and private-data exclusion.
- The authenticated workspace has a **tab-only, opt-in** Dashboard/Orders client probe. Open `/dashboard?navTiming=1` in the test browser tab to enable it there; `/dashboard?navTiming=0` disables it. The switch persists only in that tab's `sessionStorage`, not in a user profile or on the server. A normal primary-sidebar click to Dashboard or Orders starts the timer; after the destination's server content mounts and the measured post-effect frame has passed, the console emits one readable `workspace_navigation_ready` line. Its JSON has only the fixed `dashboard`/`orders` route label and rounded durations: `durationMs` (click to measured frame), `readyEffectMs` (click to the destination's React ready effect), `effectToPaintMs` (that effect to the measured frame), and `routeResourceCount`. If a matching same-origin route `fetch` started after the click, it also reports `routeRequestStartMs`, `routeFetchDurationMs`, `routeResponseEndMs` and `afterResponseMs`; `responseToReadyEffectMs` is included only when that response ended before the effect. Where the browser supports Long Animation Frames, a short-lived observer adds `longFrameSupported=true`, `longFrameCount`, `longFrameOverlapMs` and `longFrameMaxOverlapMs` for frames overlapping the **ready-effect → measured-frame** interval. The overlap values are bounded to that interval and rounded to milliseconds. Unsupported or failed observers report `longFrameSupported=false` and zero counts; supported zero counts mean no captured >50 ms frame in that interval, **not** proof that the browser did no work. A third animation-frame callback only lets the prior frame's observation settle; it does not change the measured `durationMs`. The observer disconnects after logging or unmount and retains at most 200 entries. The probe inspects exact route paths only and **never logs** a resource URL, query, LoAF script attribution, customer/order identifier, content or account details, and sends no telemetry request. A zero resource count means prefetched, cached or unobserved—not that the network took zero time. Other destinations, same-page clicks and modified new-tab clicks are not samples. Read only the test tab's filtered console entries and compare their capture timestamps with the nearest matching Caddy route response. Browser throttling, a hidden tab, prefetched responses, multiple route requests and automation scheduling can affect comparison. The React effect is a lifecycle marker, not proof of first visual paint; the post-effect measured frame is an approximation, not a main-thread trace. These bounded timings are **not** a full network waterfall. Disable the probe after a diagnostic session; never copy unrelated console entries or production page content into an issue.
- `autosale_http_requests_total` — rate/error за method, route template і status class.
- `autosale_http_request_duration_seconds` — histogram тривалості HTTP.
- `autosale_operations_total` — результат normalization та Sheets export.
- `autosale_operation_duration_seconds` — histogram фонового процесу.
- `autosale_queue_backlog{queue="google_sheets"}` — поточна кількість знайдених pending export.

Для Google OAuth відстежуйте лише tenant-safe події: connect success/failure, refresh failure за стабільним кодом, reconnect-required, cleanup retry/terminal і тривалість Sheets/Drive операції. Заборонено логувати authorization code, access/refresh token, Google email, назву/ID таблиці, назву вкладки або її рядки.

У labels заборонені order ID, request ID, URL, повідомлення помилки та інші необмежені значення.

## Початкові сигнали

- **Page:** частка `sheets_export/failure` понад 5% протягом 10 хвилин, якщо було щонайменше 20 спроб. Перевірити стан tenant OAuth, quota та останні `sheets_export_failed` за `correlationId`.
- **Ticket:** зростає кількість `REAUTHORIZATION_REQUIRED` або terminal cleanup. Власнику показати reconnect; не відновлювати grant вручну й не копіювати токени в support channel.
- **Page:** найстаріший pending export очікує понад 10 хвилин. Перевірити worker health, mounted secret і backlog.
- **Ticket:** p95 HTTP latency понад 2 секунди протягом 30 хвилин. Перевірити маршрут, PostgreSQL і зовнішні залежності.

Порогові значення треба скоригувати після накопичення реального трафіку; не додавайте pager без підключеного каналу оповіщення та перевіреного runbook.

## 2026-10-24 перевірка затримки навігації

- У тестовій production-вкладці з тимчасово ввімкненим `navTiming=1` звичайний перехід до Orders завершився за 394 мс: один route fetch — 177 мс, після відповіді до відмальованої сторінки — 214 мс. Інші завершені записи цієї короткої сесії: Orders 415 мс і Dashboard 387 мс. Вимірювач вимкнено в тій самій вкладці через `navTiming=0`; тестову вкладку закрито. Це локальні діагностичні зразки, а не розподіл досвіду всіх користувачів.
- Останні 165 наявних записів обмеженого Caddy-журналу (23 жовтня 10:25 — 24 жовтня 05:37 UTC, включно з тестовими переходами) показали для Dashboard `n=82`, p50 38 мс, p95 143 мс, max 439 мс; для Orders `n=83`, p50 34 мс, p95 103 мс, max 154 мс. Чотири записи Dashboard мали 307, решта — 200. За попередні 24 години web-журнал не містив `web_upstream_slow` або `web_upstream_failed`. Це не доводить, що періодичного повільного завантаження немає: журнал проксі не вимірює браузерний рендеринг, а поріг web-події становить 1 с.
- Search Console Core Web Vitals станом на перевірку 24 жовтня (останнє оновлення звіту — 21 жовтня) досі не має достатньо 90-денних польових даних ні для мобільного, ні для настільного типу пристрою. Не оптимізуйте за одним лабораторним прогоном як за доведеним польовим регресом. При наступному повільному переході зберіть його обмежений `workspace_navigation_ready` запис і зіставте час із Caddy та API; якщо переважає `afterResponseMs`, профілюйте браузерний рендеринг, якщо `routeFetchDurationMs` — серверний шлях. Не копіюйте в діагностику URL з параметрами, дані клієнтів або інші консольні записи.
- О 05:41 UTC ще одна тестова сесія відтворила два повільні переходи: Orders 1 402 мс (останній route response за 159 мс, решта 1 243 мс) і Dashboard 2 221 мс (response за 128 мс, решта 2 093 мс). Найближчі відповіді Caddy були HTTP 200 за 87 і 59 мс. Причина післявідповідної паузи ще не доведена; нові `readyEffectMs`, `responseToReadyEffectMs` та `effectToPaintMs` розділяють її при наступному відтворенні, але не замінюють browser performance trace.
- Після web-only релізу `acbb867` 24 жовтня контрольні переходи без проміжного опитування DOM/консолі теж були повільними: Orders `durationMs=1659`, `effectToPaintMs=1309`, один довгий кадр перекрив 788 мс; Dashboard — 2015, 1676 і 1004 мс відповідно. Обидва маршрути відображалися, `longFrameSupported=true`; після `navTiming=0` нових записів не було. Це підтверджує внесок довгих кадрів у конкретні зразки, але не показує джерело виконання. Не трактуйте решту паузи або нуль кадрів як доказ відсутності браузерної роботи; наступний крок — цільовий DevTools trace під час повільного переходу, без копіювання атрибуції з приватними URL до журналу.
