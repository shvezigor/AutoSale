## Contextual route-loading follow-up

Commit `be3d931` replaced the generic workspace loading animation with route-specific headings, accessible status text and layout placeholders. The status changes after three seconds to acknowledge a longer wait without claiming a percentage or inventing progress. Reduced-motion users do not receive the delayed reveal animation. The UI contract and feature index were updated with the implementation.

Verification before deployment: 104 web test files and 495 tests passed; web TypeScript checking and the production Next.js build passed. Component tests cover all seven route contexts, the three-second status change and timer cleanup. An isolated 320 px browser viewport showed no horizontal overflow for the new Orders loading component; this fixture was not the authenticated production shell and must not be treated as a production mobile visual acceptance.

After a web-only production deployment, an authenticated Ukrainian workspace at 1280 px showed the contextual loading state during Dashboard and Settings navigation, followed by the completed destination pages. Orders loaded its table. A screenshot of the completed Settings state was captured in the browser session, but no production screenshot artifact was stored because that screen contains account details. No site-scoped browser errors were observed during these checks. Public `/health/live` returned 200 and the web container was healthy. The deployment used verified backup `backups/20261022T090911Z` (manifest checksums, PostgreSQL dump listing and MinIO archive listing checked). API and worker containers were not redeployed.

Not yet proven: a forced slow/failing production request, an authenticated mobile production viewport, and the underlying cause of intermittent API 5xx incidents. The loading redesign improves feedback but does not itself make requests faster or provide a retry action.

## Mobile dashboard overflow correction

An authenticated production Chrome pass at 390 px found the dashboard document `scrollWidth` at 641 px; a visually hidden, semantically exposed chart-data `<table>` retained a roughly 609 px intrinsic width and escaped its own `sr-only` clipping. The same read-only mobile pass loaded Conversations, Orders, Catalogue, Settings and Onboarding without document-width overflow. This is a dashboard-specific layout defect, not evidence that the intermittent route-loading delay is fixed; one Orders transition still displayed the long-wait placeholder before its content appeared.

The chart now puts its semantic table inside a visually clipped wrapper. It remains available by table name to assistive technology, while the wrapper owns the one-pixel clipping box. A component regression first failed on the former table-level `sr-only` markup and then passed with the wrapper; all 500 web tests, web typecheck, production build and the existing dashboard Playwright fixture tests passed. The authenticated production mobile dashboard and broader width/keyboard acceptance must be repeated after web-only deployment before closing this correction.

## Intermittent-delay diagnostic baseline

On 22 October, 12 additional authenticated Dashboard ↔ Orders browser transitions completed in 449–568 ms (median 535 ms); no long wait or 5xx was reproduced. The running API histogram at that point recorded 29 `GET /api/orders` requests, 28 within 250 ms and all 29 within one second. This is a process-lifetime snapshot, not a historical latency distribution. The web container's preceding two hours of logs contained no errors, but it did not record the duration of its internal API calls. Therefore the current evidence does not support a database/query optimization as the fix for the intermittent symptom.

The follow-up adds safe web-to-API timing/error diagnostics. Only calls at least one second long, HTTP 5xx and network failures are logged, with a fixed route group, status class, duration and request ID forwarded to the existing API telemetry. The logs intentionally exclude full paths, query text, cookies, response bodies and exception messages. The next observed slow incident can now be split into the web-to-API hop and API request duration; a slow browser navigation with neither event still requires separate Next/edge/client investigation. This is instrumentation, **not a claimed speed improvement or a resolution of the earlier unidentified 5xx**.
