# Глобальні стани завантаження, нотифікації та меню профілю

Дата: 2026-09-04
Статус: погоджено для планування

## Мета

Користувач AutoSale має завжди розуміти, коли система виконує дію у фоні, чим вона завершилася та де знайти важливі події пізніше. У верхній частині робочої області також має бути стабільне місце для нотифікацій і керування профілем.

## Обсяг першої версії

Перша версія додає:

- глобальний застосунковий header для авторизованих сторінок;
- індикатори завантаження трьох рівнів;
- toast-сповіщення у верхньому лівому куті робочої області;
- постійний центр важливих нотифікацій;
- меню профілю з переходами й виходом;
- інтеграцію з імпортом каталогу, Google Sheets і збереженням налаштувань.

Не входять у першу версію: push-нотифікації браузера, email-розсилки, WebSocket/SSE, користувацьке налаштування категорій нотифікацій та окрема сторінка повного архіву.

## Принципи UX

1. Інтерфейс не блокується, якщо користувач може безпечно продовжувати роботу.
2. Кнопка, яка запустила дію, показує локальний стан і не допускає повторного запуску.
3. Фонові операції показуються тонкою смугою прогресу у верхній частині робочої області.
4. Повноекранний або секційний overlay використовується лише тоді, коли подальші дії можуть спричинити конфлікт.
5. Завершення дії завжди має явний результат: успіх, помилка, попередження або інформація.
6. Toast повідомляє про результат зараз; центр нотифікацій зберігає важливий результат для подальшого перегляду.

## Структура інтерфейсу

### App header

На всіх авторизованих клієнтських сторінках над основним вмістом з’являється компактний header. Ліворуч він містить назву поточного розділу або залишається нейтральним, щоб не дублювати великий заголовок сторінки. Праворуч розташовані:

1. кнопка нотифікацій із лічильником непрочитаних;
2. кнопка профілю з аватаром або ініціалами;
3. випадаюче меню профілю.

Меню профілю містить ім’я, email, роль, посилання «Налаштування», посилання «Команда» лише для власника та дію «Вийти». Поточний блок профілю й окрема кнопка виходу внизу бокової навігації видаляються.

На мобільних пристроях header залишається компактним і не перекриває основну навігацію. Поповери вирівнюються по правому краю viewport і не виходять за його межі.

### Loading-стани

Передбачено три рівні:

- **локальний** — spinner і дієслово на кнопці, наприклад «Перевіряємо…»;
- **секційний** — skeleton для першого завантаження таблиць, списків або карток;
- **глобальний фоновий** — тонкий progress bar під header, коли виконується одна або декілька довгих операцій.

Глобальний менеджер активностей зберігає кількість паралельних операцій. Індикатор зникає лише після завершення останньої. Анімації поважають `prefers-reduced-motion`.

### Toast-сповіщення

Toast stack розміщується зверху зліва всередині робочої області після бокової навігації. На мобільних він займає ширину з безпечними відступами.

Типи: `success`, `error`, `warning`, `info`. Кожен toast має заголовок, необов’язковий короткий опис, іконку типу та кнопку закриття. Success/info автоматично закриваються через 5 секунд, warning — через 8 секунд, error залишається до закриття користувачем. Наведення або фокус призупиняє таймер.

Контейнер використовує `aria-live="polite"`; критична помилка має `role="alert"`. Toast не отримує фокус автоматично й не перериває робочий сценарій.

### Центр нотифікацій

Кнопка-дзвіночок відкриває popover із останніми 20 нотифікаціями поточного користувача в межах його tenant. У панелі доступні:

- лічильник непрочитаних;
- список із типом, текстом і відносним часом;
- перехід за `actionUrl`, якщо подія має пов’язаний екран;
- позначення елемента прочитаним під час відкриття;
- дія «Позначити всі прочитаними»;
- зрозумілий порожній стан.

Нотифікації належать конкретному користувачу, а не всім учасникам tenant. Адміністратор платформи не отримує доступу до клієнтських нотифікацій або їхнього змісту.

## Модель даних і API

Таблиця `UserNotification`:

- `id`;
- `tenantId`;
- `userId`;
- `type`: `SUCCESS | ERROR | WARNING | INFO`;
- `category`: стабільний машинний ідентифікатор події;
- `title`;
- `message` — необов’язкове коротке пояснення без секретів;
- `actionUrl` — необов’язковий внутрішній шлях;
- `readAt`;
- `createdAt`.

Індекси підтримують вибірку останніх записів користувача та непрочитаний лічильник. Видалення старих записів не входить у UI першої версії; сервер зберігає максимум 90 днів через окрему фонову політику очищення.

API:

- `GET /api/notifications?limit=20` — останні записи та `unreadCount`;
- `POST /api/notifications/:id/read` — позначити один запис;
- `POST /api/notifications/read-all` — позначити всі записи поточного користувача;
- внутрішній сервіс `NotificationService.create(...)` для серверних модулів.

Всі запити обмежуються `tenantId` і `userId` із серверної сесії. Клієнт не передає ці ідентифікатори самостійно. `actionUrl` приймає лише внутрішні шляхи з дозволеним префіксом, щоб уникнути open redirect.

## Потік подій

### Коротка синхронна дія

1. Компонент реєструє activity і переводить кнопку в локальний loading-стан.
2. Після успіху activity завершується та показується success toast.
3. Після помилки activity завершується, показується error toast, а локальний контекст помилки залишається біля поля або секції.

### Важлива фонова дія

1. API або worker завершує імпорт, синхронізацію чи експорт.
2. Сервер створює `UserNotification` для користувача, який ініціював дію.
3. Без realtime-транспорту перша версія оновлює центр після завершення запиту, при поверненні фокусу у вкладку та раз на 60 секунд, коли вкладка активна.
4. Новий запис одночасно може бути показаний як toast, якщо користувач знаходиться у відповідному сценарії.

## Події першої інтеграції

Постійні нотифікації створюються для:

- успішного або невдалого імпорту CSV/XLSX;
- успішної або невдалої синхронізації каталогу з Google Sheets;
- створення шаблону таблиці замовлень;
- помилки експорту підтвердженого замовлення;
- втрати або необхідності повторної Google/Instagram авторизації.

Збереження звичайної форми налаштувань показує toast, але не створює постійний запис. Це запобігає інформаційному шуму.

## Компонентні межі

- `AuthenticatedShell` — спільний layout авторизованих сторінок;
- `AppHeader` — контейнер кнопок нотифікацій і профілю;
- `ProfileMenu` — доступне dropdown-меню;
- `NotificationCenter` — отримання й відображення постійних нотифікацій;
- `ToastProvider` / `useToast` — короткі клієнтські повідомлення;
- `ActivityProvider` / `useActivity` — облік паралельних фонових дій;
- `LoadingButton`, `RouteSkeleton`, `SectionSkeleton` — повторно використовувані loading-компоненти;
- `NotificationService` — створення і читання нотифікацій із tenant/user isolation.

Компоненти popover закриваються по `Escape`, кліку поза областю та після переходу. Фокус повертається до кнопки-тригера. В один момент відкритий лише один popover.

## Обробка помилок

- Помилка завантаження центру нотифікацій не блокує сторінку; popover показує компактний retry state.
- Невдале створення постійної нотифікації логуються, але не перетворює успішну бізнес-операцію на помилку.
- Клієнтські toast не містять сирі відповіді API, токени, email інших користувачів або технічні stack trace.
- Повторний клік під час mutation блокується локальним loading-станом.

## Доступність

- Усі тригери є нативними `button` з доступними назвами.
- Badge має окремий screen-reader текст про кількість непрочитаних.
- Dropdown підтримує клавіатуру, видимий focus ring, `Escape` і повернення фокуса.
- Skeleton позначає секцію `aria-busy="true"` та має текстовий опис для screen reader.
- Інформація не передається лише кольором: кожен стан має іконку й текст.
- Контраст відповідає WCAG 2.1 AA.

## Адаптивність

Перевіряються ширини 320, 768, 1024 і 1440 px. На вузьких екранах:

- toast stack має відступ 12 px і не перекриває навігацію;
- notification popover використовує доступну ширину viewport;
- текст профілю ховається, але аватар і доступна назва залишаються;
- skeleton повторює мобільну структуру контенту.

## Тестування

### Backend

- tenant/user isolation;
- непрочитаний лічильник;
- read/read-all;
- валідація `actionUrl`;
- створення нотифікацій із вибраних бізнес-сценаріїв;
- відмова запису нотифікації не ламає основну операцію.

### Frontend

- черга і таймери toast;
- error toast не закривається автоматично;
- activity counter з паралельними операціями;
- відкриття, закриття та keyboard navigation popover;
- профільні пункти відповідно до ролі;
- unread badge і read-all;
- loading, error та empty states;
- інтеграційні тести для Google Sheets, імпорту каталогу й налаштувань.

### Перевірка браузером

- відсутність console errors;
- tab order і focus return;
- responsive breakpoints;
- reduced motion;
- відсутність перекриття toast, header і мобільної навігації.

## Критерії готовності

1. Кожна підключена операція показує стан виконання й явний результат.
2. Важливі події зберігаються для конкретного користувача та доступні через дзвіночок.
3. Непрочитаний лічильник і read/read-all працюють після перезавантаження.
4. Меню профілю замінює дубльований профіль у боковій панелі.
5. Компоненти доступні з клавіатури й адаптивні на визначених ширинах.
6. Всі автоматизовані тести, typecheck і production build проходять.
