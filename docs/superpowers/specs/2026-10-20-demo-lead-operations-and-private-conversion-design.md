# Demo lead operations and privacy-minimal conversion measurement

**Status:** implemented and manually deployed on the current Docker host on 2026-10-20. Public production-browser checks pass with controlled 429/503 response interception. On 2026-10-21, isolated Redis-backed concurrency, expiry, established-client disconnection, stopped-server unavailability and Nest HTTP 429/`Retry-After`/idempotent-replay/503 checks passed with fictional data. The named tunnel's `proxy:80` route and loopback-only Caddy host binding are deployed and browser-checked; a controlled live Cloudflare-header, quota, replay and browser-429 check also passed. A partial platform-admin browser acceptance covers the masked queue, fictional-lead detail/status persistence, aggregate conversion report and count-only notification metrics; actual step-up exports and authenticated automated cases remain open. Authenticated owner acceptance is partial, while legal analytics activation and independent erasure-ledger gates remain open. The two collection/erasure switches remain off.

## Outcome and boundaries

Protect the public demo request without losing legitimate retries, give platform operators a deliberate and audited way to process requests, and stop retaining demo contacts indefinitely. Add first-party conversion reporting without visitor profiling. Finish the outstanding browser accessibility checks for existing forms. This extends the existing `DemoLead`, durable notification worker, platform-admin shell, auth limiter, security audit, shared form controls, and pricing registry; it does not create another lead database or move tenant data into platform administration.

The work is five independently testable increments: public abuse protection; admin lead queue; contact export/deletion/retention; privacy-minimal conversion reporting; and form accessibility acceptance. Existing SMTP/provider and tenant physical-deletion gates are not part of this change.

## Options considered

1. **Selected: extend the existing PostgreSQL lead and admin capability.** Redis holds only short-lived limiter counters, PostgreSQL owns leads, status transitions and audits, and the existing admin shell hosts the queue. Server-derived conversions and aggregate anonymous counters avoid cross-site visitor identity. This reuses existing access and recovery paths.
2. Adopt a CRM, CAPTCHA and third-party analytics package. Faster dashboards, but extra processors, consent and credential handling, vendor lock-in, and another source of truth. Rejected for this stage.
3. Add only a mail notification and a spreadsheet of contacts. Small initial build, but no safe operator state, audit, bounded retention or recoverable export. Rejected.

## 1. Public form abuse protection

- Keep `POST /api/demo-leads` and its existing validation, idempotency key and database-first acceptance. Cap the JSON request body at 16 KiB and add one invisible, screen-reader-excluded honeypot as a low-friction bot signal. A honeypot hit receives a generic accepted-looking response but persists no lead; it is not the only defence.
- Use Redis atomic counters with expiring keys, separately for a trusted client IP (`10` new requests per 10 minutes) and a normalized contact HMAC (`3` new requests per 24 hours). Never trust an arbitrary browser-supplied forwarding header; use the configured proxy trust boundary. No raw IP, email or phone enters Redis keys, logs or metrics. A repeat of an already accepted idempotency key is returned as the same accepted lead and does not consume another quota.
- Rate limits are a bounded configuration with conservative defaults and tests for multiple API instances, simultaneous requests, expiry, spoofed headers and legitimate retries. A limit returns HTTP 429 with `Retry-After`; Redis outage fails closed with a safe 503. The form localizes both states at form level, preserves entries, exposes an accessible live message and does not reset its idempotency key after a transient failure. Existing field-level validation remains intact.
- Do not add a third-party CAPTCHA or analytics cookie. Count limiter outcomes without retaining contact values.

Implementation increment (2026-10-20): the public route checks a 16 KiB raw JSON limit, suppresses a screen-reader-hidden `companyWebsite` honeypot without persistence, and returns an already accepted idempotency key before consuming quota. Atomic Redis Lua checks and increments an IP and a normalized contact counter together; defaults are 10 per IP/600 seconds and 3 per contact/86,400 seconds. Email is trimmed/lowercased; phone formatting is stripped to digits. Redis keys contain only HMAC-SHA256 digests using `AUTH_TOKEN_PEPPER`, never raw IP/contact. Caddy accepts `CF-Connecting-IP` from *any* private-network peer, replaces the API-bound forwarding chain with one parsed client address, and Express trusts exactly Caddy's hop. The tunnel is an intended private peer, but the 2026-10-21 host audit found all-interface Caddy port publication and a separate tunnel using `host.docker.internal:80`; a direct private-peer spoofing path remains conditional on firewall reachability and requires a coordinated tunnel/port hardening change. A limit returns 429 with `Retry-After`; Redis outage returns 503. The form preserves entered values and its idempotency key, with localized rate-limit and outage text announced as an error. Isolated disposable-Redis concurrency/expiry/disconnection and Nest HTTP quota/replay/error checks passed; production-browser response-interception checks passed, while the live trusted-proxy boundary remains an explicit acceptance gate.

Infrastructure increment (2026-10-21): the managed Cloudflare hostname's ingress config was confirmed as `sales-aito.com → http://proxy:80` on the private Compose edge network. A separate stale Quick Tunnel aimed at `host.docker.internal:80` was stopped without deleting its container. Caddy's host ports were rebound from all interfaces to `127.0.0.1` only. Public and localhost health, host-interface rejection, and production browser checks passed after a brief proxy-recreation 502. This removes the observed host/LAN exposure but does not change Caddy's private-peer trust rule or replace a live client-IP spoof-boundary acceptance test.

Live acceptance increment (2026-10-21): an attacker-supplied `CF-Connecting-IP` header was rejected at Cloudflare before the API, while an attacker-supplied `X-Forwarded-For` reached API but did not split the hashed per-IP Redis counter across three accepted fictional leads. The fourth request for the same fictional contact received HTTP 429 with a positive `Retry-After`; an accepted-key replay returned its original ID without a new quota increment. The production browser displayed the 429 alert without losing input. This closes the tested public-tunnel client-IP/quota path, but not the broader trust of arbitrary private Docker peers or a destructive live-Redis outage.

Network-boundary review (2026-10-23): a read-only container attached only to the current `autosale_edge` network reached both `api:3001/health/live` and `worker:3002/health/live` directly with HTTP 200. These two services did not need `edge`: Caddy reaches API through `internal`, while the named tunnel reaches only Caddy through `edge`. The scoped Compose fix removes `api` and `worker` from `edge`, preserving their internal connectivity and outbound Docker NAT. `infra/scripts/verify-edge-network-boundary.ps1` asserts the rendered topology and, with `-Live`, verifies actual memberships and that only the proxy health route remains reachable from an edge-only probe. This closes the direct edge bypass only after deployment and live acceptance; Docker daemon access or compromise of a trusted internal application peer remains a separate host-security boundary.

## 2. Platform-admin lead queue

- Add `/admin/leads` to the existing admin navigation, separate from tenant clients. A paginated and filterable table shows creation time, company, status, notification state and masked contact; no note or full contact in the list. A detail route reveals the contact and optional note only to an authenticated `PLATFORM_ADMIN`, with no caching or indexing.
- Existing lifecycle values remain `NEW`, `CONTACTED`, `QUALIFIED`, `CLOSED`. Permitted operator transitions are explicit and validated; reopening a closed lead returns it to `CONTACTED`, not a new row. The API uses an expected version/updated timestamp to reject conflicting edits. There is no tenant conversion, assignment, outbound customer message, or arbitrary free-text operator note in this slice.
- Record status changes, contact-detail access, export and deletion in the existing platform security-audit mechanism with actor ID, lead ID, action, old/new status where applicable and time. Never copy name, contact, note or CSV into audit metadata. Audited mutations and status change commit atomically; audit failure rolls the mutation back. Admin overview/operations stay aggregate-only.
- Admin screens use the shared buttons and loading states, localized safe errors, keyboard focus and responsive table/detail layouts. A tenant member gets no route or API access, including by direct URL.

Implementation increment (2026-10-20): `/api/admin/demo-leads` and `/admin/leads` provide a bounded 50-row page with stable `createdAt,id` ordering and cursor continuation. The list selects only company, masked contact, lifecycle/notification status, creation time and version; name, full contact and note are withheld. The detail route selects full contact only for a platform administrator, returns `Cache-Control: no-store` and appends `DEMO_LEAD_DETAIL_ACCESSED` with lead UUID only before disclosing the response. A status mutation follows `NEW→CONTACTED→QUALIFIED→CLOSED` or explicit `CLOSED→CONTACTED`, compares the expected version and appends `DEMO_LEAD_STATUS_CHANGED` with UUID and enum values in one database transaction. The additive migration adds a version counter and `last_operator_action_at`; an audit failure rolls the mutation back. The existing admin shell adds a separate Demo requests navigation item; status action uses `LoadingButton`, localized conflict/error text and the established responsive table/detail patterns. Deployed code and automated checks pass, but platform-admin browser acceptance remains open.

## 3. Demo contact lifecycle

- Product rule approved on 2026-10-20: identifiable lead contact lives no more than **180 days after the last operator action and no more than 365 days from creation**. Last operator action means a successful lifecycle change; reading a lead or sending internal notification does not extend retention. The earliest deadline wins. A data-subject request may delete earlier. These are product defaults requiring legal review before EU general availability, not a universal statutory retention claim.
- Add a nullable `lastOperatorActionAt` and compute the deterministic expiry from it and `createdAt`; a bounded worker sweep uses PostgreSQL as source of truth. After fencing active notification claims, the sweep physically deletes the `DemoLead` row and commits a minimal purge audit with lead UUID, time and reason only. The existing platform-audit helper must support a system actor without inventing a human administrator. No original contact, note or original idempotency key survives in that audit. A replay after purge is a new public request subject to validation and abuse limits; it can never recover the erased record. Concurrent notification and erasure use a fenced claim/transaction so no post-erasure email is sent.
- Platform admin may export one lead as a same-origin UTF-8 JSON attachment after purpose-bound five-minute password step-up. A scoped CSV export of a date/status-filtered set is capped and streamed without intermediary public object storage; spreadsheet formula-leading values are escaped. Export and access are audited. No contact is included in generic admin metrics, queue payloads or logs.
- An admin can request early deletion with step-up, confirmation of the lead ID and an audit trail. Deletion must fail safely if a notification is in-flight, then retry once it is terminal; it must not silently destroy an accepted request before the operator sees the outcome. The privacy notice and request instructions explain the purpose, period, access/export and deletion path. Backups age out under the existing schedule; restore procedure must replay the deletion ledger before access.
- Use fictional data in migrations/tests. A dry-run count, idempotent worker sweep, interrupted-run recovery and same-origin export download are acceptance gates before enabling scheduled erasure in production.

Implementation increment (2026-10-20): the existing admin password reauthentication now has separate five-minute `DEMO_LEAD_EXPORT` and `DEMO_LEAD_DELETE` purposes. A same-origin, no-store JSON attachment exports one contact; date/status-filtered CSV pages through at most 1000 rows, refuses larger matches and escapes formula-leading cells. Successful exports audit only lead UUID or date/status/count. Early deletion requires exact UUID confirmation, refuses active notification leases and commits row deletion plus contact-free audit atomically. The admin UI uses shared buttons, localized field errors and preserved entries. Code is deployed but browser acceptance is pending. Production deletion remains gated on an independently recoverable erasure ledger: the database audit alone cannot prevent a pre-deletion backup from resurrecting a contact.

Retention increment (2026-10-20): an additive worker-only PostgreSQL function selects at most 100 expired rows with `FOR UPDATE SKIP LOCKED`, fences active notification leases, physically deletes eligible leads and appends a `SYSTEM` audit with UUID/reason in one database call. Disposable PostgreSQL tests pass exact 180/365-day deadlines, operator-action extension, active/expired leases, lock contention and replay-after-purge. The API and worker both default `DEMO_LEAD_ERASURE_ENABLED` to false; the UI hides early deletion and the worker never invokes purge until a verified off-host deletion ledger, dry run, backup/test restore and legal/browser acceptance make activation safe. The migration and worker code are deployed but purging is disabled.

## 4. First-party conversion measurement

- Fixed event vocabulary: `pricing_view`, `plan_interest`, `registration_arrival`, `account_registered`, `first_order_confirmed`, `demo_intent`. The name, purpose, trigger, deduplication key and permitted properties are documented alongside the contract. Plan ID is from the approved pricing registry; locale and day are bounded enums/date. No free text, URL query, IP, user agent, email, phone, customer message, provider ID, third-party cookie or cross-site identifier is stored.
- Anonymous pricing and registration page views and plan interest produce daily aggregate counters only; there is no anonymous visitor history or individual session stitching. `demo_intent` is counted once when an accepted `DemoLead` row is created, not from a button click. `account_registered` is counted from successfully created tenant accounts, **not** the anonymous `registration_arrival` counter. `first_order_confirmed` is that tenant's first approved, non-demo order, regardless of manual or automatic approval; it is a separate first-value metric, never called trial activation. Derive both from canonical server-side transitions rather than browser beacons. The actual 30-day trial start/enforcement is not implemented and is **not** inferred from registration or order analytics; its product policy remains in the monetization document. Authenticated plan-interest can use an internal tenant ID while needed for the first-order-to-interest funnel; raw linkage expires after 90 days and is never exposed in an admin response. Aggregate daily counts may remain for up to 13 months. Do not claim that anonymous pricing views can be individually attributed to later registrations.
- The signed-in dashboard includes a small **Обговорити тариф / Discuss a plan** action, approved by the owner on 2026-10-20. It opens a clear plan-choice/contact panel. Selecting a plan records a deduplicated tenant-scoped interest event and offers an email action to contact Sales AITO; it does not charge, subscribe, change access, promise a callback, or silently submit personal contact data. A failed measurement does not block the email action. The UI explains that billing is not yet active.
- `/admin` reporting shows date-bounded aggregate totals, including registration-to-first-order and first-order-to-plan-interest, and clearly labels denominators and incomplete attribution. Low-volume cells are suppressed where they could reveal a single organization. No event feed, per-user drilldown or raw payload is exposed.
- Update the public privacy notice before enabling collection, and keep collection off until the notice/event contract and legal basis are reviewed for the intended markets. Document a disable switch and deletion/reconciliation procedure. A failed analytics write never blocks registration, first-order confirmation or demo acceptance.

Implementation increment (2026-10-20): the fixed public schema accepts only `pricing_view`, `registration_arrival` and `plan_interest` with `uk`/`en` and an approved plan ID where required; identifiers, URLs, free text and server-derived event names are rejected. `/api/conversion/events` enforces a 2 KiB body limit and an HMAC-IP Redis quota of 60 per hour before calling a narrow PostgreSQL increment function. The table stores only UTC day, event, locale, plan sentinel and count. The API database role may call the increment function but cannot read raw daily rows; a disposable PostgreSQL test proves this boundary. `MARKETING_ANALYTICS_ENABLED` defaults to false pending privacy/legal review. `demo_intent` is derived from accepted canonical `DemoLead` rows in aggregate reporting rather than duplicating a fallible write; this preserves exact-once acceptance without letting analytics failure block a demo request. Public page signal payloads passed production-browser inspection; authenticated interest and admin reporting browser acceptance remain pending.

Public-signal increment (2026-10-20): the localized pricing page sends one `pricing_view` event per mount and each plan CTA sends a fixed `plan_interest` with approved plan ID. The registration page sends one `registration_arrival` event per mount. The best-effort same-origin requests contain no URL, query, contact, cookie identifier or free text; the normal navigation still works on collection failure. Because server collection remains disabled by default, these UI events do not yet produce production counters. Canonical registration, demo and first non-demo order counts will be calculated from database rows in the platform report; no browser event can claim those outcomes.

Authenticated/reporting increment (2026-10-20): owner/manager sessions may record one tenant-plan interest per approved plan and UTC day through an RLS-scoped transaction, only while the analytics switch is enabled. The dashboard offers a direct email link and a "Discuss a plan" action; email remains available even when the event write fails. The action does not subscribe, charge, alter access or promise a callback. A fixed, date-bounded platform-admin rollup returns public action counts, canonical tenant registration/demo-lead counts, first approved non-demo order per tenant, and two explicitly defined cohorts. The server suppresses every cell below three and only exposes cohort rates when both counts are at least three; plan-interest cohort rates are unavailable outside the 90-day linkable window. The underlying security-definer function returns aggregates only, and its API-role execution is exposed solely through the platform-admin route. A bounded worker sweep deletes raw tenant interests older than 90 days and daily counters older than 13 months. This code is deployed but not browser-accepted in authenticated sessions and does not authorize collection activation.

## Security, rollout and acceptance

- Every admin API remains `PLATFORM_ADMIN`-guarded. Step-up tokens are purpose-bound and checked against the current session. Admin responses use `Cache-Control: no-store`; download uses same-origin attachment headers. No tenant-user route exposes demo leads.
- All migrations are additive first. Historical leads receive the approved absolute cap without changing current notification status. Purging is enabled only after a verified backup, dry-run count, test restore and proof that notification races are fenced. Roll back application code without rolling back contact-erasure migrations or resurrecting erased data.
- TDD covers limiter concurrency/replay, authz, transition/audit atomicity, export escaping, retention boundaries, notification race, analytics deduplication/minimization and accessibility contracts. Run focused suites, whole typecheck/build and browser acceptance on the deployed environment. Verify success, invalid/rate/error states, persistence after reload, admin downstream state and 320–1440 px screenshots. If platform-admin credentials or provider access is unavailable, leave the exact live gate open; never claim the whole release complete on code tests alone.
- Keep `docs/features/README.md`, marketing/platform-admin/retention canonical documents, privacy notice, release runbook and acceptance checklists in sync as each increment lands. Commit verified scoped increments, merge/push `master`, delete the short-lived branch and clean only this task's worktree once unique changes are proven absent.
