# Internal AI provider usage ledger and unit-cost measurement

**Date:** 2026-10-24
**Status:** In progress. Approved by the owner in chat on 2026-10-24. The tenant-scoped ledger, store, lifecycle-export dataset and shared Responses transport boundary are implemented in the feature branch; production adapter wiring, reporting, reconciliation/retention and deployment remain pending.

## Outcome and boundary

The operator needs a defensible estimate of direct AI and infrastructure cost per canonical order before validating Sales AITO plan economics. Workers need a tenant-scoped record of each actual AI provider invocation, including calls that produce no order or usable reply. This is an **internal measurement** capability. It does not charge tenants, start trials, enforce limits, expose usage in the customer workspace, or change the approved order-count value metric in the [monetization hypothesis](../../product/2026-09-17-sales-aito-monetization.md).

PostgreSQL remains the source of truth. Existing `orders`, `order_intent_evaluations`, `ai_reply_drafts` and `catalogue_mappings` retain their product/audit metadata but are not summed as a cost ledger: an intent evaluation and its order can describe the same response, mapping can batch multiple responses, and a parsed-invalid or timed-out response can lose usage before those records are finalized. The current five worker-side OpenAI adapters are `openai-order-recognizer`, `openai-reply-draft-generator`, `openai-table-structure-analyzer`, `openai-column-mapper` and `openai-ambiguous-row-classifier`. The last currently returns no usage metadata; the others coerce missing usage to zero. Historical values are incomplete evidence, not an authoritative backfill.

## Options considered

1. **Selected: one minimal tenant-scoped provider-call ledger at the existing worker adapters.** It records numeric usage and safe execution metadata before business parsing, then supports a private, invoice-reconciled monthly report. This captures ignored intent checks, invalid drafts and each catalogue batch without creating a billing system. The extra database writes and adapter changes are the cost.
2. Sum the existing product tables. Smaller change, but double-counts order/intent responses and misses invalid, interrupted and multi-batch calls. It cannot support a trustworthy cost claim.
3. Use only the provider's account-level billing dashboard. Good control total, but it cannot attribute spend to tenant or operation, explain setup cost, or detect one tenant's high-cost flow. Keep it as the reconciliation source, not the sole ledger.

## Data flow and ownership

- A small worker-owned metering boundary wraps the five existing adapters; it does not create another model client, job queue or order service. Each *application invocation* has a newly generated attempt UUID, tenant UUID, one bounded purpose (`ORDER_RECOGNITION`, `ORDER_INTENT`, `REPLY_DRAFT`, `CATALOGUE_STRUCTURE`, `CATALOGUE_COLUMN_MAPPING`, `CATALOGUE_ROW_CLASSIFICATION`) and an internal operation UUID. A catalogue batch gets its own attempt. Safe deterministic fallbacks that never call the provider create no attempt.
- The adapter records a `STARTED` attempt immediately before the provider boundary. It finalizes usage as soon as a response is received, **before** JSON/schema/factual validation. Invalid model output can therefore have real usage. A returned response with no usage is `USAGE_MISSING`, never zero. A transport error or timeout after dispatch is `CHARGE_UNKNOWN`, not assumed free. A provable pre-dispatch failure is `NOT_SENT`.
- A bounded reconciler converts an orphaned `STARTED` row past its lease into `CHARGE_UNKNOWN` without repeating the provider call. It cannot infer token usage from the business record or treat a missing provider response as free.
- An explicit application retry creates a **new** attempt, even for the same order/draft/mapping operation. Repeated finalization of one attempt is idempotent and cannot add usage twice. SDK-level hidden retries must be audited during implementation; either expose each transport attempt or disable those retries with regression coverage before claiming one row per possible charge. Existing durable job idempotency and provider-send rules remain unchanged.
- A metering insert/finalization failure must not silently report zero. During this non-billing measurement phase it does not by itself block an otherwise valid order or draft; it emits a bounded content-free failure signal and marks the reporting interval provisional through invoice reconciliation. No customer text, generated answer or raw provider error is logged. Before metering could ever influence entitlements or billing, this best-effort boundary requires a separate reliability and authorization decision.

## Ledger contract

An additive `ai_provider_usage_attempts` table has a tenant ID and attempt UUID, purpose, operation UUID, provider (`OPENAI` for this slice), requested and returned model identifiers, start/finalized timestamps, outcome, nullable non-negative input/output token counts and nullable priced sub-counts when the provider returns them (for example cached input). It stores a bounded error category, not an exception message or provider payload. A `BEFORE UPDATE` trigger rejects all changes to terminal rows; this slice provides no correction procedure. A `STARTED` row can be finalized once. Database constraints reject negative or contradictory usage; `NULL` means unavailable and numeric `0` means the provider explicitly reported zero.

`REPORTED` requires explicitly known input and output totals; the cached-input breakdown may be absent. `USAGE_MISSING` requires at least one missing total and retains any known total or subcount. Cached input requires a known input total and cannot exceed it. `STARTED`, `CHARGE_UNKNOWN` and `NOT_SENT` require all token counts to be `NULL`. Started rows have no finalized timestamp, returned model or error category; terminal rows require a finalized timestamp no earlier than their start. Error categories are limited to `TRANSPORT_ERROR`, `TIMEOUT`, `PRE_DISPATCH_FAILURE` and `ORPHANED`.

The database package exports `AiProviderUsageStore`, constructed with a Prisma client, and `AiUsageContext = { tenantId, operationId, purpose }`. `start(context, requestedModel, attemptId, now)` persists `STARTED` with constant provider `OPENAI`. `finalize(context, attemptId, outcome, usage, returnedModel, now, errorCategory?)` conditionally updates only the matching tenant/operation/purpose attempt still in `STARTED` and returns whether one row changed. Each usage field is individually nullable; callers supply an all-null usage object when no counts are available. Both operations use `withTenantTransaction`. Duplicate or competing finalizations cannot add usage twice. API has tenant-scoped read permission but no insert/update/delete permission; worker has tenant-scoped read/insert/update permission and no direct deletion permission. Runtime-role bootstrap preserves these restrictions.

The table contains no prompt, conversation content, catalogue row, customer identifier, email, phone, address, URL, access token, raw provider response or API key. Internal operation UUIDs are tenant-confidential and never become log/metric labels or public API fields. Forced fail-closed RLS and the existing `withTenantTransaction` pattern protect reads/writes; runtime roles get the minimum required rights. A PostgreSQL isolation test must prove empty context and cross-tenant reads/writes fail. Platform-admin APIs do not gain row-level access in this slice.

This is tenant-owned operational data: include it in the canonical lifecycle export while held, prevent new provider calls for a frozen tenant under the existing freeze gates, and permit finalizing an already-dispatched attempt so a freeze does not erase cost evidence. The proposed engineering retention for raw attempts is 90 days, subject to the privacy/accounting review before production activation. A bounded, idempotent sweep and its lifecycle/restore acceptance must ship with production collection, so records are not silently retained forever; retain longer tenant-linked summaries only after a separate legal/accounting decision. The normal backup expiry and later deletion-ledger replay still apply.

The canonical lifecycle export now includes `ai-provider-usage-attempts`, selecting only the ledger's fourteen scalar fields. Exact allowlist, real JSONL archive count/checksum and PostgreSQL tenant-isolation tests cover the schema slice. No provider adapter calls the store yet, and the bounded orphan reconciler and retention function will arrive in a follow-on migration before production collection. No deployment or live browser/provider acceptance is claimed for this stage.

The worker's `ai-usage/metered-responses.ts` now owns a shared, independently tested non-streaming Responses boundary and an injectable OpenAI client factory with `maxRetries: 0`. Each call generates a new attempt UUID, awaits start before one SDK invocation, enforces `store: false`, and awaits finalization before returning the original response without parsing generated text. Counts must be integers from zero through PostgreSQL INTEGER's maximum; invalid or missing values stay NULL. Valid partial totals survive. Cached counts require a known input total; a cached count above that total makes both input and cached evidence unknown while preserving valid output, yielding `USAGE_MISSING`. Missing or otherwise invalid cached breakdowns stay NULL independently of known totals.

Transport exceptions finalize as `CHARGE_UNKNOWN` with all counts NULL and a fixed `TIMEOUT` or `TRANSPORT_ERROR` category, then rethrow the original exception. Start-storage failure still permits the single provider invocation; finalization failure or a false conditional-update result preserves the original product result. The only failure-signal arguments are `start_failed` and `finalize_failed`, and a failing signal sink cannot replace the response or exception. Adapter integration, worker bootstrap changes and the existing tenant-freeze gates remain the next collection step; the tested boundary and factory are not active in production call paths yet.

## Internal monthly report

The first reader is an operator-only, read-only report/CLI, not a tenant UI or new unauthenticated endpoint. It uses an explicit tenant scope under the worker's existing RLS transaction pattern; any global rollup iterates a bounded, authorized tenant directory instead of issuing an unrestricted cross-tenant table read. The report groups attempts by their `startedAt` UTC calendar month and orders by their `createdAt` UTC month; calls spanning a month boundary are a reconciliation caveat. It can show a tenant's totals only in a private operator context and does not write its output to Git, logs or a public dashboard. It shows calls and known tokens by purpose/model; `CHARGE_UNKNOWN`, `USAGE_MISSING`, metering failures and unpriced model buckets remain visible as coverage gaps. Existing product-table token columns are diagnostic comparisons only, never added to ledger totals.

Rates are versioned, effective-dated operator inputs sourced from the provider's actual tariff/invoice and kept outside the repository. The calculation keeps the provider invoice currency; it prices only usage dimensions whose rates and provider sub-counts are known. A missing cached-token breakdown or rate produces an unpriced bucket, not a guessed amount. The operator reconciles computed provider charges with the account invoice after accounting for credits and taxes. A verifiable Sales AITO project/account boundary is required to exclude unrelated provider usage; without one, or with any unexplained variance, the period stays **provisional**. No current OpenAI rate, exchange rate or infrastructure invoice is embedded in code or this specification.

For each period, the denominator is the count of distinct canonical tenant `orders.id` created in that period, not AI attempts, status changes, exports or webhook retries. Technical/test tenants are excluded only by an explicit operator-maintained cohort list, never a name heuristic; their AI spend is shown separately and excluded from the pilot unit-economics numerator too. All **included** tenant AI spend in that period—including ignored order-intent checks, failed/unused drafts and one-time catalogue setup—is in the numerator, with setup shown separately. Zero-order tenants show spend and an undefined per-order ratio, never a zero cost. Physical order deletion is not currently enabled; if it becomes possible, an immutable order-usage source must replace counting surviving rows before any billing decision.

Direct infrastructure cost is a **separate** monthly invoice input for Sales AITO host/storage and other attributable service resources. The report presents the actual shared total and a global blended cost per canonical order; it does not fabricate precise per-tenant infrastructure allocation without a measured allocation basis. If the host also serves technical/test workloads, their share needs an approved allocation or the blended figure remains provisional. Labour, taxes, payment-provider charges and customer carrier/provider message fees are excluded and labeled as such. A period with a missing invoice, unknown provider spend or an unapproved allocation cannot be called complete or used to assert the monetization document's 30%-of-revenue threshold. Test-account samples do not validate willingness to pay or production unit economics.

## Rollout and verification

1. Add the ledger schema, RLS, role grants and lifecycle-export coverage with fictional-data migration/isolation tests. No historical authoritative backfill; pre-rollout months are labeled incomplete.
2. Instrument one shared call boundary and the five adapters. Tests cover successful usage, explicit zero versus missing usage, invalid parsed output, provider timeout/unknown charge, multi-batch mapping, ignored intent, explicit retry, duplicate completion, insert/finalize failure and tenant freeze. Prove no payload or tenant/operation ID enters metrics/log labels.
3. Add the private month/model/purpose report and invoice-input validation. Test order/intent double-count avoidance, zero orders, test-tenant exclusion, missing rate/breakdown/invoice and reconciliation variance. Do not expose tenant totals through platform aggregate endpoints.
4. Release additively after backup. Verify worker/API health, queue behavior and a fictional/authorized test-tenant browser flow for catalogue mapping, order recognition and draft generation, including persistence after reload where relevant. Do not send a customer reply or create external shipments merely to verify metering. Compare the private ledger with provider invoice totals before using any cost-per-order result for pricing; if the live provider/account is unavailable, record the exact open acceptance gate.

The implementation is complete only when the current month can be reported with explicit coverage and reconciliation status, no double counting, tenant isolation and no customer-data exposure. It does **not** complete billing, the five-store AI-draft pilot, production SMTP or legal approval for subscriptions.
