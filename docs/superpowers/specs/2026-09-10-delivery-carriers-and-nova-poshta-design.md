# Служби доставки та створення ТТН

## Мета

Менеджер AutoSale має створювати відправлення без повторного введення даних із замовлення. Перша інтеграція — Нова пошта. Архітектура одразу підтримує додавання Meest та Укрпошти окремими адаптерами без зміни моделі замовлення або інтерфейсу менеджера.

У першій версії зовнішнє відправлення створюється лише після явного підтвердження менеджера. Автоматичне створення ТТН без перегляду не входить до цього етапу.

## Погоджені продуктні правила

- PostgreSQL залишається джерелом істини для замовлень, відправлень, статусів та аудиту.
- Доставка має окремий життєвий цикл і не перевантажує `Order.status` або procurement-статуси.
- В одному замовленні може бути лише одне активне відправлення першої версії. Скасовані та помилкові спроби зберігаються в історії.
- ТТН створюється лише для підтвердженого замовлення, яке готове до виконання. Позиції мають бути `IN_STOCK` або `RECEIVED`; незавершена закупівля блокує створення.
- Менеджер перевіряє точного одержувача, відділення або адресу, вагу, місця, габарити, оголошену вартість, платника й післяплату перед створенням.
- Повторний клік, мережевий retry або перезапуск worker не створюють другу накладну.
- Після успішного створення менеджер отримує підготовлений текст із ТТН і окремо підтверджує його надсилання клієнту в Instagram.
- Повна автоматизація створення ТТН і надсилання повідомлення клієнту відкладається до накопичення production-статистики.
- Банківські рахунки та повний модуль оплат реалізуються після доставки. Перша версія доставки підтримує ручне значення оголошеної вартості та післяплати без прив'язки до банківського рахунку.

## Варіанти інтеграції

Обрано прямі адаптери перевізників за спільним контрактом `DeliveryProvider`.

- `NOVA_POSHTA` реалізується зараз через офіційний API 2.0.
- `MEEST` додається другим. Доступ до API зазвичай потребує договору з Meest.
- `UKRPOSHTA` додається третім через офіційний API Укрпошти.

Сторонній агрегатор не використовується: він додає платну залежність, ще одного одержувача персональних даних та не потрібен для першої вертикальної версії.

## Підключення Нової пошти

У `Налаштування → Доставка` власник робочого простору:

1. Вставляє API-ключ зі свого бізнес-кабінету Нової пошти.
2. AutoSale перевіряє ключ запитом до API, але не повертає його у браузер після збереження.
3. Обирає контрагента-відправника, контактну особу, телефон та стандартну адресу або відділення відправлення.
4. Задає стандартного платника доставки, тип вантажу, вагу, кількість місць і габарити.
5. Вмикає або вимикає пропозицію повідомити клієнта після створення ТТН та редагує шаблон повідомлення.

Ключ шифрується тим самим серверним механізмом захисту секретів, що й інші tenant credentials. UI показує лише стан `Підключено`, дату перевірки та безпечну помилку. Власник може замінити ключ або відключити інтеграцію. Менеджер може користуватися підключенням, але не читати чи змінювати секрет.

## Універсальний домен доставки

### З'єднання

`DeliveryConnection` зберігає:

- `tenantId`, `provider`, `status`;
- посилання на зашифрований credential;
- безпечний account label;
- час останньої успішної перевірки та безпечний код помилки;
- користувача, який підключив або відключив інтеграцію.

Одна активна конфігурація кожного перевізника дозволена на tenant. Provider-specific ідентифікатори відправника зберігаються у `DeliverySenderProfile`, а не в загальному `TenantSettings`.

### Відправлення

`Shipment` зберігає:

- `tenantId`, `orderId`, `provider`, `status`;
- snapshot відправника й одержувача на момент підтвердження;
- тип доставки: відділення, поштомат або адреса;
- стабільні provider references міста, відділення та адреси;
- місця, вагу, габарити, опис, оголошену вартість і післяплату;
- платника доставки та спосіб оплати доставки;
- provider document ID, номер ТТН, розраховану вартість;
- idempotency key, версію спроби та безпечний error code;
- час створення, прийняття перевізником, доставки, скасування та останньої перевірки.

Необроблена відповідь перевізника не повертається у frontend. Для діагностики зберігається лише мінімальний санітизований snapshot без API-ключа та зайвих персональних даних.

### Статуси

Внутрішній `ShipmentStatus` не копіює нестабільні коди конкретного API:

- `DRAFT` — дані підготовлені, зовнішнього документа немає;
- `CREATING` — намір зафіксований, зовнішній результат ще невідомий;
- `CREATED` — ТТН отримана, але посилка ще не прийнята перевізником;
- `ACCEPTED` — посилку прийнято;
- `IN_TRANSIT` — посилка рухається;
- `DELIVERED` — доставлено;
- `RETURNING` — оформлено або почалося повернення;
- `RETURNED` — повернуто відправнику;
- `CANCELLED` — відправлення скасоване до завершення;
- `FAILED` — остаточна помилка створення або синхронізації, що потребує дії.

Окремий mapper перетворює provider status code на внутрішній статус і зберігає останній зовнішній код для підтримки. Невідомий код не змінює стан навмання, а створює метрику й потребу повторної перевірки.

## Контракт адаптера

Кожен адаптер реалізує вузький типізований контракт:

- `validateCredential`;
- `listSenderProfiles`;
- `searchCities`;
- `searchLocations` для відділень і поштоматів;
- `calculateShipment`;
- `createShipment`;
- `getShipmentStatus`;
- `getLabel`;
- `cancelShipment`.

Вхідні й вихідні дані перевіряються схемами. Відповіді зовнішнього API вважаються недовіреними. Provider-specific поля не проникають у контракти сторінки замовлення.

## Створення ТТН

1. Менеджер відкриває підтверджене й укомплектоване замовлення.
2. AutoSale створює або повертає локальний `DRAFT` зі snapshot даних замовлення та tenant defaults.
3. Текстове відділення з AI extraction використовується лише як пошукова підказка. Менеджер підтверджує точний запис із довідника перевізника.
4. API перевіряє ПІБ, телефон, location reference, вагу, місця, оголошену вартість та правила післяплати.
5. Перед підтвердженням виконується розрахунок вартості; його помилка не створює ТТН.
6. Після підтвердження сервер атомарно переводить shipment у `CREATING` та фіксує idempotency key формату `shipment:create:v1:<shipmentId>:<version>` разом із hash запиту.
7. Worker викликає Нову пошту. Успіх записує provider document ID, ТТН, вартість і `CREATED`.
8. Timeout має стан `unknown`, а не автоматичний повтор створення. Reconciler спочатку шукає документ за стабільним client reference і лише потім вирішує, чи можна повторити виклик.
9. Паралельний або повторний запит повертає поточне відправлення й не проходить до провайдера вдруге.

## Інтерфейс замовлення

Після секції комплектації показується картка `Доставка`.

До створення:

- стан готовності та зрозуміла причина блокування;
- кнопка `Створити відправлення`;
- уже заповнена форма в modal/drawer, адаптивна для мобільного;
- пошук міста та відділення з debounce, loading і keyboard navigation;
- попередній розрахунок вартості;
- явне остаточне підтвердження.

Під час створення:

- кнопка має стабільну ширину, spinner і текст `Створюємо ТТН…`;
- повторні дії блокуються лише в межах картки/діалогу;
- глобальний toast повідомляє про довгу операцію або помилку, але сторінка не перезавантажується.

Після створення:

- номер ТТН, перевізник, тип доставки, вартість та локалізований статус;
- дії `Скопіювати ТТН`, `Завантажити маркування`, `Відстежити`, `Скасувати`;
- історія попередніх скасованих відправлень у згорнутому блоці;
- кнопка `Повідомити клієнта` з редагованим preview тексту.

Таблиця замовлень отримує компактний статус доставки та фільтр без зміни чинної пагінації. На мобільному статус входить у картку замовлення.

## Повідомлення клієнту

Перша версія не надсилає повідомлення автоматично. Після успішного `CREATED` AutoSale формує текст із назвою tenant, номером ТТН і безпечним tracking link. Менеджер може відредагувати текст та натиснути `Надіслати клієнту`.

Надсилання використовує чинний Instagram outbound pipeline, зберігає provider message ID та не змінює shipment при помилці Instagram. Якщо платформа не дозволяє повідомлення в поточному вікні переписки, UI показує зрозумілу помилку й залишає ТТН доступною для копіювання.

## Фонове відстеження

- Reconciler обирає активні shipment записи за `nextStatusCheckAt` і ставить безпечні jobs.
- Частота опитування залежить від стану: рідше для `CREATED`, частіше після `ACCEPTED`, припиняється для terminal status.
- Retry використовує exponential backoff і provider rate-limit hints.
- Зміна статусу записується в `ShipmentStatusEvent` з внутрішнім та зовнішнім кодом без customer PII.
- Важливі переходи можуть створювати наявні in-app/Telegram user notifications, але це не блокує доставку.

## API AutoSale

- `GET /api/integrations/delivery` — безпечний список підключень.
- `PUT /api/integrations/delivery/nova-poshta` — перевірити та зберегти ключ; лише owner.
- `DELETE /api/integrations/delivery/nova-poshta` — відключити майбутні операції без видалення історії.
- `GET/PUT /api/integrations/delivery/nova-poshta/sender-profile` — прочитати або зберегти defaults.
- `GET /api/delivery/locations?provider=&query=&cityRef=&type=` — tenant-scoped пошук довідника.
- `POST /api/orders/:orderId/shipments/quote` — валідація та розрахунок без side effect.
- `POST /api/orders/:orderId/shipments` — створити локальний намір і повернути `202` з shipment summary.
- `GET /api/orders/:orderId/shipments` — активне відправлення й історія.
- `POST /api/shipments/:id/cancel` — скасувати з ідемпотентним наміром.
- `GET /api/shipments/:id/label` — проксі/stream документа лише авторизованому tenant member.
- `POST /api/shipments/:id/customer-message` — підтверджене менеджером повідомлення через поточний conversation.

State-changing endpoints використовують CSRF, tenant scope, role checks та idempotency. Cross-tenant ID повертає той самий безпечний результат, що й відсутній запис.

## Помилки та відновлення

- Невірний або відкликаний ключ: connection стає `NEEDS_ATTENTION`; чинні shipment записи не видаляються.
- Немає точного відділення: ТТН не створюється, менеджер обирає запис із довідника.
- Timeout створення: стан залишається `CREATING/unknown`, повторна кнопка не доступна до reconciliation.
- Provider validation error: показуються локалізовані поля для виправлення без сирого payload.
- Остаточна помилка: shipment переходить у `FAILED`; менеджер може виправити дані й створити нову version.
- Скасування після фактичного прийняття може бути недоступним; UI пояснює наступну дозволену дію.
- Недоступність Instagram не відкочує створену ТТН.

## Безпека та приватність

- API-ключі зашифровані, маскуються і не потрапляють у frontend, логи, audit changes або telemetry.
- Телефон, ім'я та адреса передаються лише обраному перевізнику для виконання доставки.
- Логи містять tenant/shipment correlation IDs, provider operation, latency та safe error code без payload.
- Історія відправлення видаляється або анонімізується за чинною retention-політикою tenant; відключення інтеграції не руйнує аудит.
- Власник керує connection; менеджер створює та обслуговує shipment; перегляд обмежений поточним tenant.

## Спостережуваність

Метрики першої версії:

- успішність і p95 latency перевірки ключа, quote, create, status і label;
- кількість `unknown outcome`, reconciliation success та duplicate prevention;
- provider validation failures за safe code;
- час `CREATED -> ACCEPTED -> DELIVERED`;
- частка ТТН, після яких менеджер надіслав повідомлення клієнту;
- скасування й повторне створення.

## Тестування й rollout

- Contracts: discriminated provider schemas, status mapping, additive compatibility.
- Integrations: fake HTTP для кожного методу Нової пошти, malformed responses, auth, rate limits і timeouts.
- Database: tenant isolation, one active shipment, version history, atomic idempotency та status events.
- API: owner/manager permissions, CSRF, quote без side effect, create `202`, duplicate clicks, cancel і label authorization.
- Worker: success, retryable, terminal, unknown outcome recovery та background status mapping.
- Web: settings flow, searchable location picker, stable loading, mobile drawer/modal, shipment card і customer-message preview.
- Privacy regression: API key та customer PII не з'являються в logs/errors/telemetry.
- Production acceptance: реальний ключ, одна контрольована ТТН, перевірка дублювання, label, status sync, cancel where allowed і ручне Instagram-повідомлення.

Rollout виконується additive: migration, API/worker з feature flag, web, підключення тестового tenant, production acceptance, після чого feature flag відкривається іншим tenant.

## Межі першої версії

Не входять:

- автоматичне створення ТТН без менеджера;
- автоматичне надсилання ТТН клієнту;
- кілька активних посилок або часткові відправлення одного замовлення;
- міжнародна доставка;
- кур'єрський pickup, переадресування, повернення та реєстри передачі;
- повний облік платежів, банківські рахунки та фінансова звірка;
- Meest та Укрпошта в першому production slice.
