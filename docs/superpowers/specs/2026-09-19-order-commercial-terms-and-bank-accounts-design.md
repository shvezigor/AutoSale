# Комерційні умови замовлення та банківські рахунки

## Мета

AutoSale має автоматично визначати, скільки клієнт повинен сплатити за замовлення, і показувати лише той рахунок компанії, який справді підходить до юридичної особи та валюти цього замовлення.

Цей етап створює надійну основу для майбутнього обліку фактичних платежів, звірки післяплати й банківських інтеграцій. Він не прирівнює підтверджене, закрите, відправлене або доставлене замовлення до оплаченого.

## Погоджені продуктні правила

- PostgreSQL залишається джерелом істини для комерційних умов, юридичних осіб і рахунків.
- Очікувана сума формується автоматично з незмінних snapshot-цін позицій і кількості.
- Факт отримання грошей є окремою подією. Статус замовлення або доставки сам по собі не створює оплату.
- Менеджер не вводить очікувану суму з нуля, якщо каталог має однозначну актуальну ціну й валюту.
- Якщо ціни немає, валюти позицій конфліктують або товар не зіставлено з каталогом, система не вигадує суму й вимагає перевірки.
- Рахунки завжди фільтруються на сервері за tenant, юридичною особою, валютою та активністю. Frontend не є межею безпеки.
- Неактивний рахунок не можна обрати для нового замовлення, але історичне посилання на нього зберігається.
- Комерційні умови клієнтського замовлення не пов'язані з майбутньою оплатою підписки AutoSale.

## Межі реалізації

### Перший етап

- довідник юридичних осіб tenant;
- довідник банківських рахунків;
- один основний активний рахунок для пари `юридична особа + валюта`;
- snapshot ціни, валюти та суми кожної позиції;
- автоматичний subtotal і загальна сума замовлення;
- вибір юридичної особи, валюти й сумісного активного рахунку в замовленні;
- явний стан `потребує заповнення`, якщо суму неможливо визначити безпечно;
- аудит змін комерційних умов.

### Наступний етап

- ручна реєстрація фактично отриманих оплат і повернень;
- стани `не оплачено`, `частково оплачено`, `оплачено`, `переплата`, `повернено`;
- звірка післяплати з даними перевізника;
- банківські та платіжні інтеграції;
- фінансові звіти й reconciliation queue.

## Варіанти архітектури

### Обрано: комерційні умови зараз, ledger оплат окремим етапом

Перший етап зберігає очікувану суму й реквізити отримувача. Другий додає окремий незмінний ledger фактичних рухів коштів. Це не дозволяє випадково позначити замовлення оплаченим лише через доставку або approval.

### Відхилено: один великий фінансовий модуль

Одночасна реалізація реквізитів, оплат, повернень, afterpayment reconciliation і банківських webhook значно збільшує ризик помилок у грошових станах і ускладнює production acceptance.

### Відхилено: лише текстові реквізити в замовленні

Вільний текст не гарантує tenant isolation, правильну валюту, активність рахунку або історичну відтворюваність і не може бути надійною основою для автоматичної звірки.

## Доменна модель першого етапу

### `TenantLegalEntity`

- `id`, `tenantId`;
- коротка назва для інтерфейсу та повна юридична назва;
- тип суб'єкта та необов'язкові реєстраційні реквізити;
- `active`, `createdAt`, `updatedAt`;
- ознака основної юридичної особи tenant.

Tenant має щонайбільше одну активну основну юридичну особу. Деактивація заборонена, поки вона використовується як default для нових замовлень; історичні замовлення не видаляються.

### `TenantBankAccount`

- `id`, `tenantId`, `legalEntityId`;
- зрозуміла назва, IBAN, назва банку;
- ISO 4217 currency code;
- `active`, `isDefault`, `createdAt`, `updatedAt`.

Для однієї юридичної особи може бути кілька рахунків в одній валюті, але лише один активний default. IBAN нормалізується перед перевіркою унікальності; повний номер доступний лише авторизованим членам tenant і не потрапляє в telemetry.

### `OrderCommercialTerms`

Окремий one-to-one запис для замовлення:

- `tenantId`, `orderId`;
- `legalEntityId`;
- `bankAccountId`, якщо сумісний рахунок обрано;
- `currency`;
- `itemsSubtotal`, `discountAmount`, `deliveryAmount`, `totalAmount`;
- `pricingStatus`: `READY` або `NEEDS_REVIEW`;
- безпечні reason codes для неповної ціни;
- версія, автор і час останньої зміни.

У першому етапі `discountAmount` і `deliveryAmount` мають нульове значення, доки для них не з'явиться окремий погоджений UI. Поля вводяться в модель зараз, щоб формула total була стабільною та не потребувала міграції існуючих snapshot пізніше.

### Snapshot позиції

`OrderItem` отримує:

- `unitPriceSnapshot`;
- `currencySnapshot`;
- `lineTotalSnapshot`;
- ідентифікатор або версію джерела ціни.

Ціна копіюється з каталогу в момент створення чи явного перевибору товару. Наступна зміна ціни товару в каталозі не переписує вже оформлене замовлення.

## Автоматичний розрахунок

1. AI формує позиції та зіставляє їх із каталогом за чинним безпечним pipeline.
2. Для кожного однозначно зіставленого товару система копіює поточну ціну й валюту каталогу.
3. `lineTotalSnapshot = unitPriceSnapshot * quantity` з decimal arithmetic і правилами округлення валюти.
4. Усі позиції мають мати одну валюту. Автоматична конвертація не виконується.
5. `itemsSubtotal` дорівнює сумі line totals; `totalAmount = itemsSubtotal - discountAmount + deliveryAmount`.
6. Якщо всі дані повні, `pricingStatus = READY`; інакше `NEEDS_REVIEW`, total не вважається підтвердженим.
7. Основна юридична особа tenant підставляється автоматично.
8. Якщо для юридичної особи й валюти є default active account, він підставляється. Якщо сумісний рахунок єдиний, його також можна підставити. Інакше менеджер обирає зі вже відфільтрованого списку.

Підтвердження замовлення не створює запис фактичної оплати. Відправлення, `DELIVERED` або procurement completion також не змінюють фінансовий стан.

## Виправлення замовлення

- Зміна кількості до початку fulfillment перераховує line total і total за збереженою unit price snapshot.
- Перевибір товару до fulfillment копіює нову snapshot-ціну й валюту та повторно перевіряє сумісність рахунку.
- Якщо валюта змінилася, несумісний рахунок автоматично відв'язується; система не залишає приховано неправильні реквізити.
- Після початку procurement handoff або створення активного shipment комерційні snapshot не редагуються звичайним order editor. Майбутня корекція має бути окремою audited adjustment operation.
- Усі зміни записуються в наявний order audit із попередніми й новими безпечними значеннями, без повного IBAN.

## Існуючі замовлення

Міграція не підставляє історичну ціну з поточного каталогу мовчки: вона могла змінитися після оформлення.

- існуючі замовлення спочатку не мають підтверджених commercial terms;
- сторінка показує `Суму не зафіксовано`;
- менеджер може відкрити preview на основі поточного каталогу й явно зберегти snapshot до початку fulfillment;
- замовлення з уже розпочатим fulfillment залишаються без ретроспективно вигаданої суми.

## Інтерфейс налаштувань

У `Налаштування → Оплата` показується hub за чинним accordion-патерном. Початково всі елементи закриті.

1. `Юридичні особи` — список, статус, основна entity, створення й редагування.
2. `Банківські рахунки` — список із entity, валютою, маскованим IBAN, статусом і default marker.

IBAN нормалізується до верхнього регістру без пробілів перед відправленням. Форма перевіряє формат до API-запиту та показує конкретну помилку біля поля; для українського IBAN обов'язкові префікс `UA` і 29 символів.

Керувати довідниками може owner. Manager бачить безпечні реквізити в замовленні й може вибрати сумісний рахунок, але не створює та не редагує рахунки.

## Інтерфейс замовлення

Окрема картка `Оплата` показує:

- автоматично розраховану суму й валюту;
- статус повноти розрахунку та конкретну причину блокування;
- юридичну особу;
- лише активні сумісні рахунки;
- маскований IBAN у selector та повні реквізити в контрольованому preview/copy action;
- пояснення, що це сума до сплати, а не підтвердження отримання коштів.

Якщо рахунку немає, UI пропонує owner перейти до налаштувань, але не дозволяє вибрати рахунок іншої entity або валюти. Відсутність рахунку не блокує готівкове чи післяплатне замовлення, якщо payment method не вимагає банківських реквізитів; повна модель payment methods належить наступному етапу.

## API першого етапу

- `GET/POST /api/settings/legal-entities`;
- `PATCH /api/settings/legal-entities/:id`;
- `GET/POST /api/settings/bank-accounts`;
- `PATCH /api/settings/bank-accounts/:id`;
- `GET /api/orders/:id/commercial-terms`;
- `PUT /api/orders/:id/commercial-terms` для дозволених pre-fulfillment змін;
- `POST /api/orders/:id/commercial-terms/preview` для явної ініціалізації legacy order без side effect.

State-changing endpoints використовують CSRF, tenant scope, role checks та optimistic version. Cross-tenant identifiers повертають той самий безпечний результат, що й відсутній запис.

## Контракти та інваріанти

- Грошові значення передаються як decimal strings, а не JavaScript floating-point numbers.
- Валюта — нормалізований трилітерний ISO code.
- `totalAmount` завжди обчислюється сервером; клієнт не надсилає довірений total.
- Обраний `bankAccountId` має належати тій самій entity, tenant і валюті та бути active на момент нового вибору.
- Історичне замовлення з деактивованим рахунком зберігає посилання й snapshot реквізитів; воно не перемикається автоматично на інший рахунок.
- Усі мутації idempotent або version-checked; подвійний клік не створює дубльовану entity чи account.

## Помилки та відновлення

- Немає ціни: `NEEDS_REVIEW` з указанням позиції; total не показується як готовий.
- Різні валюти: менеджер має виправити товари або умови; автоматичної конвертації немає.
- Рахунок деактивовано між відкриттям і збереженням: API відхиляє stale selection і повертає оновлений сумісний список.
- Одночасна зміна комерційних умов: optimistic version conflict без перезапису чужих даних.
- Помилка автоматичного розрахунку не змінює order approval і не видаляє попередній валідний snapshot.

## Безпека та приватність

- Усі запити tenant-scoped; entity/account IDs не є глобальним доступом.
- Повний IBAN не потрапляє в logs, metrics, toast, audit changes або error payload.
- Видалення довідника замінюється деактивацією, якщо існують історичні посилання.
- Реєстраційні дані юридичної особи й рахунки не експортуються в Google Sheets без окремого погодженого mapping.
- Тестові fixtures використовують тільки явно вигадані реквізити.

## Спостережуваність

- кількість автоматично готових і неповних pricing snapshots;
- safe reason codes для `NEEDS_REVIEW`;
- конфлікти entity/currency/account;
- optimistic version conflicts;
- частка нових замовлень, де сума й рахунок визначені без ручної дії.

Метрики не містять сум, IBAN, назв клієнтів або реквізитів entity.

## Тестування та rollout

- Database: tenant isolation, decimal precision, one default entity/account, deactivation with history, concurrency.
- Contracts: decimal strings, currency validation, additive nullable fields for compatibility.
- API: owner/manager permissions, CSRF, cross-tenant access, active filters, stale version, server-side total.
- Order creation: complete catalogue price, missing price, mixed currencies, quantity correction and product replacement.
- Web: closed accordion defaults, mobile forms, filtered account selector, loading/error states and legacy preview.
- Regression: existing order approval, procurement, delivery and Google Sheets export continue to work without commercial terms.
- Migration: additive nullable schema first, backfill defaults only for newly created entities/accounts, no historical price invention.

Rollout: migration → API read compatibility → settings UI → automatic snapshots for new orders → order payment card → production acceptance on a fictional test order. Actual payment recording remains disabled until the next specification is approved.

## Критерії приймання першого етапу

1. Owner створює entity та рахунки різних валют, але може мати лише один default account на entity/currency.
2. Нове замовлення з однозначними каталоговими цінами автоматично отримує правильні line totals і total.
3. Selector не повертає рахунок іншої entity, валюти, tenant або inactive account.
4. Зміна кількості до fulfillment перераховує суму без звернення до нової каталожної ціни.
5. Зміна товару повторно створює snapshot і скидає несумісний account.
6. Старе замовлення не отримує поточну ціну без явного підтвердження менеджера.
7. Approval, shipment і delivery не створюють факт оплати.
8. Існуючі order/procurement/delivery/export сценарії проходять regression suite.
